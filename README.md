# Byawasaya — commerce SaaS for Nepal

Byawasaya is a Nepal-focused multi-tenant commerce SaaS for retailers and wholesalers. It is built with Java 21, Spring Boot, React/TypeScript, PostgreSQL, Redis and Docker, with platform administration, tenant workspaces, customer accounts, public storefronts and order workflows.

## Implemented in this branch

### Authentication and account security

- Separate platform (`/admin/login`) and tenant (`/tenant/login`) login experiences.
- Login identifier accepts email or registered mobile number.
- Persistent opaque server-managed sessions. The browser receives an `HttpOnly` cookie; raw session credentials are not returned to JavaScript or stored in browser storage.
- Multiple active sessions per account. Each session records its browser user-agent and client IP; account disablement, password changes and tenant suspension revoke all active sessions.
- Server-side logout, password change, password recovery, session revocation on account disablement and tenant suspension.
- CSRF protection for cookie-authenticated state-changing requests.
- MFA for every platform login: email OTP is used until a user enrolls an authenticator, after which TOTP or a one-use recovery code is required. Authenticator seeds are AES-GCM encrypted with a dedicated key; recovery codes are stored as hashes.
- Login/password-reset/email-verification rate limiting using PostgreSQL-backed attempt counters.
- Google OAuth authorization-code login and secure account linking to an existing email-verified tenant account.
- Email verification, one-time password-reset tokens and staff account setup links. Token hashes are stored rather than raw tokens.
- Separate `platform_users` and tenant `user_accounts` tables. The platform superadmin is bootstrapped from environment variables on first startup.
- Tenant staff invitations with one-time password setup links; staff can view products/orders, while manager memberships can update order status.

### Tenant application and approval

- Owner registration collects store name, owner name, email, mobile, citizenship number, PAN/VAT number, registration number/authority, registered address, province, district and municipality.
- Required document types: citizenship front/back, owner photograph, government registration certificate and PAN/VAT certificate.
- Document upload size/type/magic-byte checks and ClamAV scanning; private documents are AES-GCM encrypted by the backend before private S3-compatible storage (MinIO locally).
- Email verification is required before application submission.
- Applicants choose the single `classic` storefront template, a published plan and optional promotion.
- Applications have draft, submitted, review, correction, approved and rejected states. Rejection requires applicant-facing notes; internal notes are not exposed to the applicant.
- Platform reviewers can open private documents, verify/reject individual documents, request corrections and approve or reject applications.
- Approval requires the latest required documents to be verified, provisions the tenant tables, assigns the selected plan and starts its configured trial.
- Trial expiry is enforced for the merchant API, public storefront and checkout. Byawasaya subscriptions use monthly/annual manual invoices; only a verified invoice payment activates an eligible subscription. Administrators can also suspend or cancel a subscription with an audit trail.

### Tenant data and commerce

- Each newly approved tenant receives an immutable generated store code and physical table prefix such as `t_a13f09bd` (the prefix is generated by the server; it is not derived from an editable store name).
- Tenant-specific tables include products, product variants, categories, staff, customers, store assets, orders, order items, payments, payment events and store settings. Variant prices are checked by the backend and copied into order snapshots.
- Dynamic tenant-table identifiers are resolved from the trusted provisioning registry and validated against an allowlist. Values remain parameterized.
- Product photos and store logos are stored as PostgreSQL `BYTEA` in the tenant's `store_assets` table; public assets are served only for operational stores.
- Checkout calculates prices on the server, validates store payment settings and uses an idempotency key to prevent duplicate orders for provisioned tenants.
- Customers can register with email/password, verify their email, sign in and view orders explicitly linked to their account.
- Store owners can connect their own eSewa and Khalti merchant accounts. Provider secrets are encrypted at rest; payment completion is recorded only after server-side provider lookup/status checks.
- Order status transitions are restricted. Cancelled/refunded orders cannot be marked paid through the manual payment endpoint.
- Product and staff limits are enforced against the assigned plan.
- The legacy shared-table path remains available for existing/demo tenants that have not been migrated. New approved tenants use prefixed tables.

### Platform administration

- Separate platform-user and tenant-user lists.
- Store application queue, document verification, review notes and approval/rejection actions.
- Tenant/store status administration.
- Plan creation, price updates, trial duration, product/staff limits and archive/delete behavior.
- Promotion codes with percentage/fixed discounts, eligibility windows, eligible plan codes, total/per-tenant limits and redemption history.
- Subscription/trial administration, monthly and annual manual invoices, tenant invoice history, audited payment receipt recording, and void/reissue controls.
- Audit records for important account, application, document, plan, promotion and subscription actions.

## Architecture and important constraints

- **Sessions are opaque tokens, not JWTs.** The database stores only token hashes while retaining per-session device and IP metadata for security review.
- **Tenant-prefixed tables are implemented for newly approved stores.** This adds migration and operational overhead compared with shared tables or per-tenant schemas. Table names must never be accepted from request parameters.
- Existing tenants using the old shared PostgreSQL tables can be migrated with `TENANT_MIGRATE_LEGACY_ON_STARTUP=true`. The migrator copies their current PostgreSQL products/orders into generated prefixed tables within per-tenant transactions. Back up first and test the migration on a copy. This option does not import data directly from an external MySQL server.
- Product images and logos use PostgreSQL `BYTEA`; private identity documents use encrypted object storage. These are intentionally separate storage policies.
- eSewa/Khalti integration is implemented but must be exercised with each tenant's real merchant account in sandbox and live environments. Refunds and provider dispute handling are not automated.
- Stores resolve at `/store/{slug}` and at `<slug>.<DOMAIN_NAME>` when the production base domain, wildcard DNS and wildcard certificate are configured. Custom-domain verification and certificate automation are not implemented.
- Subscription invoices are manual. Platform staff issue invoices and record verified full payments; tenants can view invoices in their billing workspace. Automated collection, payment retries/dunning, platform payment gateway, invoice email delivery and tax-invoice compliance are not implemented.
- Platform-admin MFA and fail-closed ClamAV scanning before identity-document storage are implemented in source; browser acceptance for enrollment/recovery and deployment acceptance for scanning remain. Production backup/restore drills, security review and penetration testing remain release blockers.

## Local setup

Requirements: Java 21+, Docker Compose, Node.js 22+ and network access to download Maven/npm dependencies on first setup.

1. Create your local environment file:

   ```bash
   cp .env.example .env
   nano .env
   ```

   Set unique values for `DB_PASSWORD`, `SUPERADMIN_PASSWORD` and `S3_SECRET_KEY`. Never commit `.env` or reuse credentials from an older archive.

2. Generate a 32-byte encryption key for private documents:

   ```bash
   openssl rand -base64 32
   ```

   Put the output in `APP_STORAGE_ENCRYPTION_KEY_BASE64` in `.env`. Do not change this key after storing documents unless you implement a key-rotation/migration procedure; losing it makes existing encrypted documents unreadable.

   Generate a separate key with the same command for `APP_PLATFORM_MFA_ENCRYPTION_KEY_BASE64`. Keep it backed up; losing or changing it makes enrolled authenticator seeds unusable. Local platform login MFA sends a six-digit email OTP by default. WhatsApp delivery is optional; configure the Meta Cloud API variables (`WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_TEMPLATE_NAME`, and `SUPERADMIN_PHONE`) before enabling it. Platform users can optionally enroll Google Authenticator and should save the one-time recovery codes.

3. Start PostgreSQL, Redis, MinIO, MailHog and ClamAV. ClamAV signature initialization may take several minutes on its first start; document uploads stay blocked until its health check passes.

   ```bash
   docker compose up -d postgres redis minio mailhog clamav
   docker compose ps
   ```

   - PostgreSQL: `127.0.0.1:5433`
   - Redis: `127.0.0.1:6379`
   - MinIO API: `http://localhost:9000`
   - MinIO console: `http://localhost:9001`
   - MailHog inbox: `http://localhost:8025`
   - ClamAV scanner: `127.0.0.1:3310` (local-only TCP; do not expose this port publicly)

4. Start the backend:

   ```bash
   set -a && source .env && set +a
   cd backend
   ./mvnw spring-boot:run
   ```

   Flyway applies `backend/src/main/resources/db/migration`. Hibernate validates the schema rather than silently changing it.

5. Start the frontend in another terminal:

   ```bash
   cd frontend
   npm install
   npm run dev
   ```

   Open `http://localhost:5173`.

### Local OAuth

To use Google sign-in, configure `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and the exact callback URL `http://localhost:8080/login/oauth2/code/google` in your Google OAuth client. Without real credentials, the Google button will not complete sign-in. Email messages can be inspected through MailHog locally.

### Email OTP login

Local development uses MailHog for email-based sign-in verification:

```env
EMAIL_MFA_ENABLED=true
EMAIL_MFA_FROM=no-reply@byawasaya.local
MAIL_HOST=127.0.0.1
MAIL_PORT=1025
MAIL_SMTP_AUTH=false
MAIL_STARTTLS=false
```

After entering a username and password, open [MailHog](http://localhost:8025) to copy the
six-digit OTP. The code expires after five minutes and is single-use. A successful code signs an unenrolled platform user in directly. Authenticator enrollment is available under Security settings; after enrollment, platform sign-ins use a TOTP code or a single-use recovery code.

### Optional legacy migration

If the old data is already present in the PostgreSQL shared tables, back up the database and set `TENANT_MIGRATE_LEGACY_ON_STARTUP=true` for one startup. The migrator provisions prefixed tables and copies products, orders and order items for active legacy tenants. Verify row counts and order totals before treating the migrated data as authoritative; keep the backup until verification is complete. Set the variable back to `false` after the migration.

## Local development proxy

The Vite development server proxies `/api`, `/oauth2`, and `/login/oauth2` requests to `http://localhost:8080` by default. Set `VITE_DEV_API_PROXY` when the backend runs elsewhere. `VITE_API_BASE_URL` remains available when using a deliberately separate API origin. Checkout requires an `Idempotency-Key` header; do not remove it from API clients.

Every platform sign-in requires a second factor. Unenrolled platform accounts use email OTP and can enter administration after verifying it. Authenticator enrollment is optional; accounts with TOTP enabled use TOTP or a single-use recovery code.
